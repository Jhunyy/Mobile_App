# Phase 3D: Core remote AI protection architecture plan

**Status: planning only. No automatic remote SMS transmission is enabled by this document.** This plan supersedes the product direction in `UPDATED_ARCHITECTURE.md`, which describes the currently implemented on-device Gemma pipeline. The Android production app should eventually use **remote Gemma 3 12B + the approved RAG knowledge as its core classifier**. Local keyword rules run first for immediate, preliminary protection. The remote result is the primary final classification. On-device Gemma is not part of the target production flow.

## What the repositories currently do

- `SmsReceiver` persists each nonempty new SMS through `SmsController.receiveAndAnalyzeRules`, then queues `SmsProcessingWorker`. The worker invokes on-device Gemma through `GemmaManager`; `MainActivity` also attempts to load that model on launch. This is not yet remote protection.
- `SmsInboxSyncWorker` reads stored inbox messages, including pre-installation messages, and sends every imported row into the same AI queue. It must not become an automatic historical upload path.
- Permission onboarding checks Android SMS permission only. It does not record informed remote-analysis consent; already granted SMS permission skips its screen. Settings has SMS, notification, contacts, and research links, but no AI Protection switch.
- `Message` and Room version 7 default `riskLevel` and `finalClassification` to `SAFE`. Current `FinalVerdictResolver` returns the rule verdict on AI failure. Thus an AI failure with zero rule matches can surface as SAFE today; Phase 3D must remove that meaning for new messages.
- The backend `POST /api/sms/analyze` requires `x-api-key` and exactly `messageId`, `sender`, `text`, and ISO timestamp `receivedAt`; success can be `SCAM`, `SAFE`, or `SUSPICIOUS` with confidence and rationale. With `RAG_ENABLED=true`, embedding or retrieval failure returns an error. Shadow mode leaves Gemma's classification as the API verdict.
- Normal Express binds to loopback. The Phase 3A/3C LAN launcher uses HTTP and a single development API key; it is for synthetic manual tests only. A compiled shared key and HTTP LAN address are not acceptable for real automatic SMS transmission.

## Product behavior and state contract

1. **First launch:** explain in plain language that full AI Protection sends each eligible newly received SMS to the remote Gemma 3 12B + RAG service. Disclose the SMS fields sent, purpose, failure behavior, and how to stop it. Request SMS permissions and then ask for a separate, explicit, initially unchecked AI Protection choice. SMS permission alone never grants remote consent. Existing installations start with remote consent **off** until they see this disclosure and opt in.
2. **After opt-in:** persist the consent version and grant time, and keep AI Protection enabled across app restarts until the user revokes it. Do not ask again for each new SMS. The receiver stores a new message and runs local rules immediately; a persistent worker sends it once to the authenticated HTTPS service if consent remains active and the endpoint is ready. The service's `classification` is the primary final verdict. Local indicators remain visible as supporting context, including when they disagree with the server.
3. **Without a completed remote result:** keep rule-positive `SCAM`/`SUSPICIOUS` as an explicitly labeled **rules-only preliminary or fallback warning**. A rule band of SAFE means only that no rule warning was found. Show **AI pending**, **AI unavailable**, **AI Protection off**, or **not analyzed remotely** as appropriate; do not show a final SAFE badge from a zero rule score. A completed authenticated server SAFE response is the only normal path to a new final SAFE verdict. A failed embedding, database lookup, model call, malformed response, or unauthorized request remains an error state.
4. **Revocation:** Settings must turn AI Protection off immediately and durably. Cancel queued work and active HTTP calls, clear/disable the runtime credential, and check the current consent generation again immediately before each network request. Do not retry or upload another message after revocation. A request already transmitted cannot be recalled; disclose this in the UI. Local rules may continue if SMS permission remains granted, labeled as limited protection. Research contribution consent is separate and is not granted or revoked by this switch.

### Eligibility and duplicate policy

An eligible message is an incoming SMS with nonempty body, received **after** the current AI Protection grant, while SMS permission and remote consent are both active. Preserve multipart assembly, `source_sms_id` uniqueness, and the existing bounded sender/body duplicate check. Maintain a stable opaque request ID for each stored message across WorkManager retries. Do not upload SMS received before consent, historical inbox imports, manually entered Phase 3B tests, or research candidates through this automatic path. If missed post-consent messages are recovered from the inbox, limit that catch-up to a disclosed time window and distinguish it from pre-consent history. The worker and server-side gateway must both handle retry/idempotency so lost responses do not cause repeated processing or alerts.

### Proposed lifecycle for new records

`RECEIVED → RULES_READY → REMOTE_QUEUED → REMOTE_RUNNING → REMOTE_COMPLETE` when consent and HTTPS/auth are ready. `RULES_READY → LOCAL_ONLY` when consent is off, and `REMOTE_QUEUED/RUNNING → REMOTE_UNAVAILABLE` or `REMOTE_CANCELLED` for a failure or revocation. Bounded, network-aware retries may move `REMOTE_UNAVAILABLE` back to queued only while the same consent grant remains active and the message is still within the disclosed retry window. Store the rule band, final verdict, verdict source, remote status, error category, and notification state separately. **UNVERIFIED is a display/assessment state, not a fourth model classification.** Do not reinterpret legacy on-device results as remote results during migration.

### Alerts and conflicting evidence

Issue one immediate local warning for strong rule evidence. When the remote response arrives, update the same message and notification ID rather than sending a second alert. The completed server verdict drives the final SCAM/SAFE/SUSPICIOUS badge; keep a visible local-indicator note if rules disagree. Define notification sound/update behavior so retries and duplicate broadcasts do not re-alert. An unavailable server never creates a SAFE verdict, and a server error is never treated as a model judgment. The experimental evidence-weighted resolver remains out of the live path.

## Release gates and open implementation decisions

1. **Consent gate:** approved disclosure, default-off migration for existing users, distinct research consent, and proof that permission alone cannot transmit SMS. No automatic network call before a current consent grant.
2. **Security gate:** trusted HTTPS endpoint with certificate validation, per-install credentials and revocation, no hardcoded shared client secret, no public Ollama/PostgreSQL, and no HTTP LAN route for real messages. Decide and document the trusted enrollment method before coding automatic submission.
3. **Reliability gate:** the MacBook Air can sleep or be offline, as Phase 2H showed. A continuously available deployment and tested offline queue/fallback are needed for a core protection claim. Define retention/retry limits and how the app displays limited protection during outages.
4. **Privacy gate:** decide whether the existing required `sender` field carries the full sender address or a minimized representation; disclose exactly what is sent. Define request, gateway, local Room, backup, and credential retention. Do not send prior inbox history merely because the user later opts in.
5. **Behavior gate:** test server-primary verdicts, local preliminary warnings, unavailable/unauthorized/RAG-error states, conflicts, notification updates, duplicate broadcasts, process death, restart, and revocation races on a physical Android device. The Phase 3B manual screen and Phase 3C browser/curl checks verify only the API path.
6. **Evaluation gate:** do not tune the frozen Phase 2E/2F/2G artifacts from these integration tests. Real-world quantitative accuracy evaluation remains deferred until the independently labeled real SMS dataset is collected and reviewed.

Only after these gates pass should a release build allow the automatic remote worker to transmit real SMS. Until then, retain the current manual synthetic-testing tools and leave automatic remote submission disabled.
