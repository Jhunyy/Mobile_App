# KA-SDS: current system and candid review

Static review of the Android app on 23 October 2026. This describes the checked-in implementation and recommends improvements. It does **not** establish measured scam detection accuracy, device reliability, security certification, or Google Play approval. No application code was changed for this review.

## What the app does today

KA-SDS receives SMS, stores messages locally, runs weighted phrase and URL-host rules, and queues every new message for on-device Gemma analysis. It presents `SAFE`, `SUSPICIOUS`, or `SCAM` in an inbox and detail screen, can notify about higher-risk messages, provides safety tips, and accepts optional feedback. Recent incoming messages from the same sender can inform Gemma and add a warning for 24 hours after a confirmed scam. [SmsReceiver.kt](app/src/main/java/com/apcida/smishingdetector/backend/receiver/SmsReceiver.kt), [SmsController.kt](app/src/main/java/com/apcida/smishingdetector/controller/SmsController.kt), [ConversationRiskPolicy.kt](app/src/main/java/com/apcida/smishingdetector/backend/detection/ConversationRiskPolicy.kt)

| Stage | Current behavior |
| --- | --- |
| Intake | An identical sender and body within 10 minutes is treated as a duplicate broadcast. The SMS is saved before rule analysis; WorkManager handles later AI work. |
| Rules | The bundled seed has 153 entries: 133 `KEYWORD` and 20 `URL_PATTERN`. Phrase matching has letter/digit boundaries. URL patterns match extracted hosts, and unlisted URLs can receive heuristic points. The seed is copied into the database only on first launch. |
| Rule score | Keyword contribution is capped at 60 and URL contribution at 80, so `riskScore` can reach 140. Scores below 30 are rule `SAFE`, 30–59 rule `SUSPICIOUS`, and 60+ rule `SCAM`. This is a weighted rule score, not a percent or probability. |
| AI | Every new, nonduplicate SMS is queued for Gemma, including a rule score of zero. The prompt includes the latest SMS, indicators, up to three earlier incoming SMS from the sender within 48 hours, and a recent confirmed scam when present. The model is requested to answer with `SCAM` or `LEGITIMATE`, `HIGH`/`MEDIUM`/`LOW`, and one reason. Invalid output is retried once within an attempt; WorkManager can make up to three attempts. |
| Final verdict | `FinalVerdictResolver` combines the rule band with the AI result and its **self-reported** confidence. A separate 0–100 `combinedRiskScore` records rule, AI, sender-history, and mismatch points; 25+ points raises an otherwise `SAFE` final verdict to `SUSPICIOUS`. The points alone do not create a `SCAM` verdict. |

The main implementation is in [KeywordEngine.kt](app/src/main/java/com/apcida/smishingdetector/backend/detection/KeywordEngine.kt), [RiskScorer.kt](app/src/main/java/com/apcida/smishingdetector/backend/detection/RiskScorer.kt), [FinalVerdictResolver.kt](app/src/main/java/com/apcida/smishingdetector/backend/detection/FinalVerdictResolver.kt), [CombinedRiskScorer.kt](app/src/main/java/com/apcida/smishingdetector/backend/detection/CombinedRiskScorer.kt), and [SmsProcessingWorker.kt](app/src/main/java/com/apcida/smishingdetector/backend/worker/SmsProcessingWorker.kt).

### Important verdict cases

- A `HIGH` or `MEDIUM` Gemma `SCAM` result produces final `SCAM`, even if the rule score is zero. A `LOW` Gemma `SCAM` result produces `SUSPICIOUS` unless the rules already found `SCAM`.
- A `HIGH` Gemma `LEGITIMATE` result can lower rule `SCAM` only to `SUSPICIOUS`. It can clear rule `SUSPICIOUS` only for a saved contact with no strong rule signal, subject to the combined-point floor. Saved contacts are **not** authenticated senders.
- A `MEDIUM` or `LOW` Gemma `LEGITIMATE` result is more conservative: `MEDIUM` cannot clear a rule warning, and `LOW` makes an otherwise rule `SAFE` message `SUSPICIOUS`.
- When Gemma is unavailable after the final attempt, rule `SAFE` becomes `SUSPICIOUS`, rule `SUSPICIOUS` stays `SUSPICIOUS`, and rule `SCAM` stays `SCAM`. The detail screen offers an AI retry.

These outcomes come from [FinalVerdictResolver.kt](app/src/main/java/com/apcida/smishingdetector/backend/detection/FinalVerdictResolver.kt) and [MessageDetailFragment.kt](app/src/main/java/com/apcida/smishingdetector/view/fragment/MessageDetailFragment.kt). Neither Gemma's confidence label nor the combined points are calibrated probabilities. `SAFE` means this policy did not keep a warning; it does not verify the sender or link.

## Compliments: what is working well

1. **A useful two-stage design.** Fast, inspectable rules can issue an early warning, while on-device contextual analysis can catch messages with no seeded phrase and can reconsider rule alerts. The final policy avoids letting a low-confidence AI answer independently declare a rule-safe message a scam.
2. **Local-first analysis.** The SMS classification path runs on the device. The app distinguishes a pending or unavailable AI result from a completed result, queues work persistently, recovers some orphaned jobs, and offers manual retry. That is a stronger prototype than one which silently drops an inference failure.
3. **More thoughtful context and signals.** The bounded same-sender history, short-message prompt guidance, host-based URL matching, credential/payment request checks, and small sender-mismatch signal address weaknesses of keyword-only detection. The strong-rule guard also prevents a saved contact from clearing a suspicious result too easily.
4. **Usable feedback loop.** The inbox has search, filters, sorting, unread state, and optional contact names; details show reasons and point contributions; reports can describe missed scams and false alerts. Report snapshots and retryable uploads make later evaluation possible. The [detection evaluation plan](DETECTION_EVALUATION.md) calls for held-out examples and false-alert measurement.

These are design and code-review compliments. I did not inspect the running UI on a device or verify detection rates.

## Negatives and the biggest factors affecting success

| Priority | Finding and likely effect | Recommendation |
| --- | --- | --- |
| **P0: distribution** | The manifest requests `READ_SMS` and `RECEIVE_SMS`, and `MainActivity` prompts for both on startup. I found no default-SMS-handler role flow and no production read of the SMS inbox. Google Play restricts these permissions. Its anti-smishing exception requires a documented track record of significant protection and review; a thesis prototype should not assume approval. | Decide the intended distribution route early. For Play, validate eligibility and prepare the required declaration and evidence before promising release. Remove any permission without a real feature need. For a research install, document the limited distribution clearly. [Google Play SMS permission policy](https://support.google.com/googleplay/android-developer/answer/10208820). |
| **P0: model availability** | Gemma loads only from the app's internal files directory or a development `adb` path. The repository does not include a user-facing model download or install flow. Without a readable model, every rule-safe message eventually becomes `SUSPICIOUS`; the main benefit of the hybrid detector disappears. | Create a reliable model delivery and first-run readiness flow; show model state to users and measure load success on the actual phones targeted. [GemmaValidator.kt](app/src/main/java/com/apcida/smishingdetector/backend/gemma/GemmaValidator.kt) |
| **P0: evidence of effectiveness** | The repository has rule/policy unit tests and an evaluation plan, but no demonstrated held-out sensitivity, precision, false-alert rate, or end-to-end device latency. The 25-point floor, thresholds, and Gemma confidence bands are policy choices. | Freeze a consented, redacted, sender/campaign-separated test set; compare rules, Gemma, and combined results; report confusion matrices by English, Filipino, and Taglish, plus failure and latency rates. Use those results to tune the alert policy. [DETECTION_EVALUATION.md](DETECTION_EVALUATION.md) |
| **P1: alert burden and speed** | Every SMS goes through CPU Gemma inference, with a 90-second timeout and up to three worker attempts. Analysis is serialized. Model failure turns even benign rule-safe SMS into flagged `SUSPICIOUS`, which may overwhelm users if the model is missing or slow. | Measure median and 95th-percentile time to final verdict, queue depth, battery/memory use, and warnings per 100 legitimate SMS. Make the pending/unavailable state unmistakable, then tune notification policy against measured alert burden. [GemmaValidator.kt](app/src/main/java/com/apcida/smishingdetector/backend/gemma/GemmaValidator.kt), [SmsProcessingWorker.kt](app/src/main/java/com/apcida/smishingdetector/backend/worker/SmsProcessingWorker.kt) |
| **P1: sensitive data and backup** | The Room database stores full SMS bodies and sender addresses. `allowBackup="true"` is set, while the checked-in backup XML files are sample templates and are not referenced by the manifest. Android's default backup can include app databases. | Specify a retention and deletion policy, then explicitly exclude sensitive data from cloud and transfer backups or set appropriate backup controls. Test backup and restore behavior. [Android Auto Backup guide](https://developer.android.com/identity/data/autobackup). |
| **P1: reporting privacy and trust** | SMS text is uploaded only if the user checks a box, which is good. However, reports also send free-text remarks, detected indicators, and Gemma rationale; these may contain phone numbers, URLs, or message fragments. The shared API key is compiled into the APK, so it should not be treated as proof that a report came from a trusted client. | Describe all fields sent before submission; minimize or redact sensitive metadata; define server retention and abuse controls. Treat the key as a rate-limiting aid, not strong client authentication. [ReportPayload](app/src/main/java/com/apcida/smishingdetector/backend/network/ReportApiService.kt), [ReportSnapshotFactory.kt](app/src/main/java/com/apcida/smishingdetector/backend/reporting/ReportSnapshotFactory.kt), [app/build.gradle.kts](app/build.gradle.kts) |
| **P1: interpretation** | Detail shows `combinedRiskScore/100`, while notifications still show the separate rule score. An AI `SCAM` verdict can appear alongside a rule score of zero. Users may read `/100` or Gemma `HIGH` as a probability, or think a saved contact proves authenticity. | Use one consistent explanation across inbox, detail, and notification: verdict, current analysis state, and concrete reasons. Label both scores as points and explain that the AI confidence label is uncalibrated. [MessageDetailFragment.kt](app/src/main/java/com/apcida/smishingdetector/view/fragment/MessageDetailFragment.kt), [NotificationHelper.kt](app/src/main/java/com/apcida/smishingdetector/util/NotificationHelper.kt) |
| **P2: update path and robustness** | Seed entries are inserted only on first launch, so changing the bundled XML will not update an existing installation. The prompt includes the full latest SMS and an unbounded list of matched indicators despite a 768-token model limit. `SmsReceiver` performs database seeding and rule work inside its broadcast window before enqueueing AI. | Version the seed and migration path. Bound prompt inputs by tokens and test long/multipart SMS. Run closed-app, reboot, burst-arrival, and slow-device tests to verify intake and recovery. [DatabaseSeeder.kt](app/src/main/java/com/apcida/smishingdetector/backend/database/DatabaseSeeder.kt), [PromptBuilder.kt](app/src/main/java/com/apcida/smishingdetector/backend/gemma/PromptBuilder.kt), [SmsReceiver.kt](app/src/main/java/com/apcida/smishingdetector/backend/receiver/SmsReceiver.kt) |

The [README](README.md) still says that no raw SMS content is ever transmitted, but the current report form offers opt-in SMS text sharing. That claim should be corrected before the app is presented to participants. The 10-minute duplicate rule can also suppress a genuinely repeated identical SMS; include repeat-message cases in device testing. [ReportFormDialog.kt](app/src/main/java/com/apcida/smishingdetector/view/dialog/ReportFormDialog.kt), [DuplicatePolicy.kt](app/src/main/java/com/apcida/smishingdetector/backend/detection/DuplicatePolicy.kt)

## Suggested next sequence

1. **Choose the release target and solve model delivery.** These determine whether the app can be installed and perform its central function outside a developer test phone.
2. **Measure real detection and alert burden on target devices.** Follow the existing evaluation plan before adjusting weights or making accuracy claims.
3. **Close privacy gaps before collecting wider feedback.** Set backup and retention behavior, clarify the report data disclosure, and revisit the compiled API key design.
4. **Polish verdict communication and reliability from measured failures.** Make pending/unavailable results clear, align the two score displays, and test closed-app and long-message paths.

This review used the checked-in source and current Google Play and Android backup documentation. It did not run Gradle tests or an instrumented device session; those are still needed to establish runtime behavior.
